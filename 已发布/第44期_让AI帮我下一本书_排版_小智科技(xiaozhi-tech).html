01

起因：一句“帮我把书下下来”

背景与需求

先交代背景。我在带一门《平面游戏设计》，32 节课，核心参考书是 The Art of Game Design: A Book of Lenses, Second Edition ——游戏设计圈公认的“透镜”方法论，原文 594 页。

课件里我给学生写了两句：

作业 1（必做）：阅读《游戏设计艺术》第 1 章。京东／当当约 60 元，不强制。

—— 我的课件原文

书不强制学生买，但我自己备课总得有一份电子版随时翻检。这种 “一次性、可复现、最好别手抄路径” 的活，正是 AI 最擅长的。

于是我在 CodeBuddy 里敲了一句：

帮我把这本书下载下来，放到 参考书 目录下，保存成 The_Art_of_Game_Design_2nd_Jesse_Schell.pdf 。

—— 我给 CodeBuddy 的唯一一句需求

就这一句。没说用什么工具，没说失败怎么办，更没提醒它 Windows 上有什么坑。

02

它的第一步很聪明：先“探路”，再动手

起飞前检查

这是我觉得它做得最专业的一步—— 它没有直接开始下载。

面对几十兆的大文件，盲下有三大风险：链接已经失效、服务器返回的其实是一个 HTML 错误页、文件大到中途断流。所以它先写了一段“探路脚本”，只发 HEAD 请求（只拿响应头，不搬数据），把三个关键信息问出来：

      PowerShell · 探路

$ProgressPreference = 'SilentlyContinue'

$urls = @(

　　@{ Name = 'ArtOfGameDesign_2nd'; Url = 'https://archive.org/download/game-design-pack/The%20Art%20of%20Game%20Design%20-%20Jesse%20Schell%20%282014%29%20%282nd%20from%202008%29.pdf' },

　　@{ Name = 'ArtOfGameDesign_archive_detail'; Url = 'https://archive.org/details/artofgamedesignsecondedition' }

)

foreach ($u in $urls) {

　　try {

　　　　$r = Invoke-WebRequest -Uri $u.Url -Method Head -UseBasicParsing -TimeoutSec 30

　　　　Write-Output ("[{0}] Status: {1}" -f $u.Name, $r.StatusCode)

　　　　Write-Output ("[{0}] Type: {1}" -f $u.Name, $r.Headers['Content-Type'])

　　　　Write-Output ("[{0}] Length: {1:N1} MB" -f $u.Name, ([double]$r.Headers['Content-Length'] / 1MB))

　　} catch {

　　　　Write-Output ("[{0}] ERROR: {1}" -f $u.Name, $_.Exception.Message)

　　}

}

注意它同时验证了两条候选地址——一条 直链 ，一条 详情页 。这就是备胎思维。

这段脚本要盯三个字段：

 

Status：200 才好，301／302 说明要跳转，403／404 直接换源；

 

Type：必须是 application/pdf 。这条最关键——很多“PDF 下载站”吐出来的是 text/html ，你下半天拿到一张写着“正在跳转到真正下载地址”的网页；

 

Length：十几 MB 合理，如果只有几十 KB，多半是个占位页。

i

写稿时我重跑了一遍

两个地址都返回「ERROR: 操作超时。」这类海外站点本来就时通时不通。这恰恰证明了“先探路”是对的：通就是通，不通立刻换源，别傻等一个十几兆的文件超时半天。

03

真正下载：一个“提速一个数量级”的开关

三个保命开关

探明真身之后，才是正式下载。第二段脚本是这样的：

      PowerShell · 下载

$ProgressPreference = 'SilentlyContinue'

$url = 'https://archive.org/download/game-design-pack/The%20Art%20of%20Game%20Design%20-%20Jesse%20Schell%20%282014%29%20%282nd%20from%202008%29.pdf'

$out = 'd:\Users\Work\Trae\2DGameDesign\参考书\The_Art_of_Game_Design_2nd_Jesse_Schell.pdf'

$dir = Split-Path $out -Parent

if (-not (Test-Path $dir)) { New-Item -ItemType Directory -Force -Path $dir | Out-Null }

Write-Output ('Start downloading...')

Invoke-WebRequest -Uri $url -OutFile $out -UseBasicParsing -TimeoutSec 300

if (Test-Path $out) {

　　$len = (Get-Item $out).Length

　　Write-Output ('Done. Size: {0:N1} MB' -f ($len / 1MB))

} else {

　　Write-Output 'FAILED: file not created'

}

看着平平无奇，里面藏着三个 Windows 上的“保命开关”：

1

关掉进度条渲染。 $ProgressPreference = 'SilentlyContinue' 是 PowerShell 5.1 的经典暗坑：默认实时渲染进度条，下载十几兆文件时，画进度条的开销远远超过下载本身，速度能慢一个数量级。加上这一行，肉眼可见地飞起来。

2

跳过 IE 引擎。 -UseBasicParsing ，否则在没初始化 IE 的机器上会直接报错。

3

给足耐心 + 自动建目录。 -TimeoutSec 300 ，目标目录不存在就自己造，绝不干等人工创建。

04

下完别急着庆祝：先问“它对不对”

看文件头，性价比最高的一招

文件落地之后，第一件事应该是：它到底是不是 PDF？

原因前面提过——服务器完全可能返回一张 HTML 错误页，而因为你指定了 -OutFile xxx.pdf ，它照样安安静静躺在你硬盘上，扩展名清清楚楚写着 .pdf 。等你双击打开，阅读器弹一句“文件已损坏”，白忙一场。

CodeBuddy 顺手给的第三段脚本，思路是看文件的二进制指纹（魔数）：

      PowerShell · 校验

$f = 'd:\Users\Work\Trae\2DGameDesign\参考书\The_Art_of_Game_Design_2nd_Jesse_Schell.pdf'

$bytes = [System.IO.File]::ReadAllBytes($f)

$head = [System.Text.Encoding]::ASCII.GetString($bytes[0..3])

$len = $bytes.Length

$tail = [System.Text.Encoding]::ASCII.GetString($bytes[($len - 10)..($len - 1)])

Write-Output ('Header: ' + $head)

Write-Output ('Size: {0:N1} MB' -f ($len / 1MB))

Write-Output ('Tail: ' + $tail)

Write-Output ('ValidPDF: ' + ($head -eq '%PDF' -and $tail -match '%%EOF'))

逻辑极简，却是我今天最想推荐的一条常识：

所有 PDF 文件开头四个字节一定是 %PDF，结尾一定有 %%EOF。头对、尾对——文件基本完整；头不对——它压根不是 PDF；尾不对——下载被截断了。

—— 今天最想让你记住的一条

这套思路可以平移： .zip 开头是 PK ，PNG 开头是 ‰PNG ，MP4 里头必有 ftyp 。 “看文件头”，是整个数字化工作里性价比最高的一招。

05

翻车现场：书是好的，我却找不到它

一个特别“中国特色”的坑

重点来了，也是这篇文章最值得记的一段。

我把上面的校验脚本原样跑了一遍，PowerShell 甩给我这么一坨：

      PowerShell · 报错原文

使用“1”个参数调用“ReadAllBytes”时发生异常:“未能找到路径

"d:\Users\Work\Trae\2DGameDesign\参考书\The_Art_of_Game_Design_2nd_Jesse_Schell.pdf"的一部分。”

所在位置 行:2 字符: 1

+ $bytes = [System.IO.File]::ReadAllBytes($f)

+ ~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~

　　+ CategoryInfo : NotSpecified: (:) [], MethodInvocationException

　　+ FullyQualifiedErrorId : DirectoryNotFoundException

上一秒刚下载成功，下一秒就“找不到路径”？

我去资源管理器里看了一眼，当场笑出声——目录确实建了，书也确实在里面，但目录名长这样：

鍙傝€冧功

这坨不知所云的字，本来应该是 “参考书” 三个字。

原因一句话： 编码打架。

 

脚本文件是 UTF-8 保存的，“参考书”三个字在 UTF-8 里是 9 个字节；

 

但 Windows 的 PowerShell 5.1 默认按系统 ANSI（中文环境就是 GBK）去读这段脚本；

 

GBK 每 2 个字节认一个汉字，于是这 9 个字节被拆成了“鍙傝€冧功”。

于是发生了一件荒唐事：下载脚本按乱码创建了目录名并成功写入文件；校验脚本拿着同一个“参考书”字符串去读，两边对不上。同一个脚本里前后字符串一模一样，却被不同环节解释成了两个不同的路径。

我用 Python 把这个目录名打印出来的时候，终端又给了我一记：

      Python · 报错原文

UnicodeEncodeError: 'gbk' codec can't encode character '\u20ac' in position 2: illegal multibyte sequence

把 Unicode 码点打出来才看清真身： \u9359\u509d\u20ac\u51a7\u529f 。

最后确认，书本身完好无损：

      Python · 验真输出

HEAD b'%PDF-1.7'

TAIL b'6\r\n%%EOF\r\n'

SIZE 14.81 MB

PAGES 594

TITLE The Art of Game Design: A Book of Lenses, Second Edition

✓

验真通过

594 页、第 2 版、标题完全正确。书是好的，只是一个目录名变成了乱码。

怎么根治？四条路，任挑一条

1

最省事：路径一律用英文。文件名本来就是英文的，中招的只有目录名。改成 refs/ 或 books/ ，一次到位。

2

要用中文就加 BOM。把 .ps1 另存为“UTF-8 with BOM”，PowerShell 才会按 UTF-8 读。

3

运行时切代码页。脚本开头加 chcp 65001 | Out-Null ，并显式设置输出编码。

4

换 PowerShell 7。新版 pwsh 默认 UTF-8，这个问题从根上消失。

!

📌 一句话记住

让 AI 写 Windows 脚本时，先把“路径不许有中文”这条写进要求里，能省掉你半小时的排查。

06

把这次经验收敛成五条法则

通用于所有交给 AI 执行的活

前面的第 36 期（编辑器扩展）、第 37 期（表情包）、第 42 期（收藏夹插件），加上这次第 4 弹，我的心得越来越收敛，就五条：

1. 给目标、给约束、给验收标准，但别替它定实现

这次我只说了“下载到这个目录、叫这个名字”。至于用 HEAD 探路、看 Content-Type、校验魔数，全是它自己规划的。AI 不缺执行力，缺的是“什么叫完成”。

2. 凡是“拿数据”的动作，都要“先探测、后执行”

先发一个便宜的请求问清楚状态码、类型、大小，再决定要不要付真金白银的流量。这条“起飞前检查”的思路，API 调用、爬虫、定时任务里统统适用。

3. 成功的标准是“结果正确”，不是“命令没报错”

命令返回 0 不代表你拿到了 PDF，“文件存在”也不代表它没被截断。看文件头、看页数、看校验和—— 把“验收”变成一个自动执行的检查动作，而不是靠眼睛扫一眼。

4. 中文路径、带空格的路径，是 Windows 脚本的头号杀手

写在源码里的中文路径，在很多环境下岁月静好，到了 Windows PowerShell 5.1 上就变成一串乱码。 跨平台的脚本，路径用 ASCII，中文留给注释。

5. 报错原文，一个字都别删地贴给它

DirectoryNotFoundException 、 UnicodeEncodeError 这些，我没有转述成“报错说找不到文件”，而是整段丢回去。 只有原始信息里才有真正的线索。

∞

小智说两句

什么叫做好了，永远得你来定义

这次总共就三段脚本，加起来不到 40 行，但它解决的是一个我每周都会碰到的真实麻烦。

回头看，整件事里我自己真正做的判断只有两个： 定目录和文件名 ，以及 “下完了要验一下” 。中间所有的坑——大文件下载慢、假链接、假 PDF、中文乱码——都是 AI 一边试一边填过去的。

AI 写代码的上限很高，但“什么叫做好了”这件事，永远得你来定义。给它画的验收红线越清楚，你的返工越少。
